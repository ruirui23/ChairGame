# 高周波椅子取りゲーム 検知アプリ 仕様書

競技「高周波椅子取り」において、可聴域外の高周波音が鳴っているか / 止まったかを機械的に検知し、参加者に低遅延で伝えるための Web アプリケーション。

---

## 1. 背景と目的

### 競技概要

- 椅子取りゲーム。音が止まった瞬間に空いている椅子へ座る。
- BGM の周波数帯が段階的に上がっていき、終盤は人間にほぼ聴こえない高周波のみになる。
- 時間 40 分 / 場所：体育館（アリーナ）/ 1 チーム 2 人。
- ルール上「自分にバフをかけるのはアリ」→ 本アプリはこの範囲内の合法な補助ツール。
- 他プレイヤーへの妨害（別の音で打ち消す等）は禁止 → 本アプリは音を発しないか、自分のイヤホン内のみに留める。

### アプリの目的

高周波が聴こえない状態でも「今鳴っている / 止まった」を正確かつ低遅延で知覚できるようにする。
特に重要なのは**「鳴り止んだ瞬間」の検知**。座るタイミングを決めるのはこの瞬間であり、ここの遅延が勝敗に直結する。

## 2. 音源の解析結果（実測済み・重要）

運営が使用する音源 5 ファイルを解析した結果。これが設計の根拠となる。

### 2-1. ファイル構成

5 ファイルはすべて同一の楽曲（長さ 650.688 秒 = 10 分 50 秒）で、高音のみを残すフィルタ（ハイパスフィルタ）を段階的に強くかけたもの。

| ファイル名 | 残っている帯域 | 用途 |
|---|---|---|
| maou_14_shining_star.mp3 | 全域（原曲） | 元の BGM |
| オーディオ_1.mp3 | 約 2,300Hz 以上 | 第 1 段階 |
| オーディオ_1-2.mp3 | 約 6,800Hz 以上 | 第 2 段階 |
| オーディオ_1-3.mp3 | 約 12,300Hz 以上 | 第 3 段階 |
| オーディオ_1-4.mp3 | 約 15,900Hz 以上 | 第 4 段階（最難） |

- 全ファイル共通で **18,200Hz より上は完全に無音**（MP3 エンコード時のローパス）。
- 競技説明の「18000 まで流れる」はこの上限を指す。

### 2-2. 最重要の発見：これは純音ではなく「音楽」

当初想定していた「18kHz の単一トーン（ピー音）」ではない。
楽曲の高音成分だけが残っている状態であり、スペクトル上に鋭いピークは立たない。

→ **検知方式は「特定周波数のピーク検出」ではなく「帯域エネルギーの測定」でなければならない。**

### 2-3. 監視帯域は 16.0〜18.2kHz の一本で足りる

4 段階すべてが 16〜18.2kHz にほぼ同等のエネルギーを持つことを実測で確認した。

| 帯域 | 段階1 | 段階2 | 段階3 | 段階4 |
|---|---|---|---|---|
| 15-16kHz | 11.4 dB | 11.4 dB | 10.9 dB | -16.4 dB |
| 16-17kHz | 11.5 dB | 11.5 dB | 11.4 dB | -5.5 dB |
| 17-18kHz | 11.0 dB | 11.0 dB | 11.0 dB | 4.4 dB |
| 18-19kHz | -4.2 dB | -4.1 dB | -4.2 dB | -7.3 dB |

→ **16.0〜18.2kHz のみを監視すれば、どの段階でも同一ロジックで検知できる。** 段階ごとの切り替え処理は不要。

（注：段階 4 のみ同帯域が約 11dB 弱い。運営が音量を上げる前提だが、キャリブレーションで吸収する）

### 2-4. 曲中の無音区間（4 ファイル共通・完全一致）

| 位置 | 長さ |
|---|---|
| 0:00.00 | 約 5.9 秒 |
| 3:53.76 | 約 5.4 秒 |
| 7:27.05 | 約 5.6 秒 |
| 10:44.80（曲尾） | 約 5.8 秒 |

これらはデジタル的に完全な無音（振幅ゼロ）。

- **運用上の扱い：無音はすべて「停止」と判定してよい**（運営が曲を流し続ける運用のため、曲由来の無音も停止として扱う）。
- そのため曲の無音と手動停止を区別する必要はなく、判定ロジックが単純化される。
- **注意点：** 曲の頭に約 5.9 秒の無音がある。運営が再生ボタンを押しても最初の 6 秒は何も鳴らないため、ゲーム開始直後の「停止中」表示は無視する。

### 2-6. 実音源での再検証（レベル3・4、`scripts/analyze.py`）

運営の実ファイル（オーディオ 1-3 / 1-4、いずれも 48kHz・650.6秒）を解析して確認した結果。**競技はレベル3から本番**（1〜2は人間が可聴）なので、この2つで設計を検証する。

| 指標（検知帯域 16-18.2kHz） | レベル3 | レベル4 |
|---|---|---|
| 音楽中レベル 中央値 | +25.7 dB | +16.3 dB（約9dB弱い） |
| 音楽の谷（5%点） | +13.6 | +5.7 |
| 無音の上端（95%点） | −39 | −42 |
| **音楽の谷 − 無音 の差** | **52.6 dB** | **47.8 dB** |

1kHz刻み（音楽中央値）：レベル3は 15-18kHz が一様に +22dB 前後。**レベル4は 15-16kHz が消滅（−5dB）し、エネルギーが 16-18kHz（特に 17-18kHz=+15.5dB）に集中**。→ 監視帯域 16-18.2kHz は両レベルで有効。

**結論：**
- 監視帯域 16-18.2kHz は正しい（レベル4でも 16-18kHz で捕捉可能）。
- 音楽と無音の差が 48〜53dB と巨大 → **停止保持60ms でも誤検知しない**ことを実証。
- レベル4はレベル3より約9dB弱い → **キャリブレーションは最弱のレベル4で行う**（レベル3は余裕で閾値超え）。
- レベル4は既知の無音4区間（0:00 / 3:53 / 7:27 / 10:45）**周辺で真の無音が断片化**（最長1.6秒の穴）。曲構造由来でランダムではない。運営の本当の停止は数秒以上続くため保持時間で区別しうるが、伸ばすと反応が遅くなるトレードオフ。既定は保持60ms据え置き。

### 2-5. この発見による設計上の利点

音楽が鳴っている時の音量の谷（最小レベル）と、真の無音（振幅ゼロ）の間には非常に大きな差がある。
そのため閾値を十分低く設定すれば、保持時間（デバウンス）を **60ms** 程度まで短縮しても誤検知しない。

当初想定の 150〜200ms から約 0.15 秒の高速化が可能。椅子取りにおいて決定的な差になる。

## 3. システム構成

```
[運営スピーカー] ──18kHz帯の音──▶ [Mac（スピーカー横に設置）]
                                        │ マイク入力
                                        │ Web Audio API / FFT解析
                                        │ 16.0〜18.2kHz の帯域エネルギー判定
                                        ▼
                                 [Mac上のローカルサーバー]
                                   Node.js + WebSocket
                                        │
                                        │ 自分のiPhoneのテザリング経由
                                        │ （ローカル通信のみ・インターネット不要）
                           ┌────────────┴────────────┐
                           ▼                         ▼
                   [iPhone A（自分）]         [iPhone B（相方）]
                   ブラウザで受信              ブラウザで受信
                   画面 + イヤホン             画面 + イヤホン
```

### 役割

| 機器 | 役割 |
|---|---|
| iPhone A（自分） | テザリング親機 兼 受信機。ネットワークのホスト |
| Mac | 検知機。スピーカー横に設置。WebSocket サーバーを兼ねる |
| iPhone B（相方） | 受信機 |

## 4. 機能仕様

### 4-1. Mac 側：検知ページ

技術： ブラウザ上の HTML + JavaScript（Web Audio API）

- `getUserMedia` でマイク入力を取得。
- **重要：** `echoCancellation: false`, `noiseSuppression: false`, `autoGainControl: false` を必ず指定する。
  これらが ON だとブラウザが高周波を「ノイズ」とみなして除去してしまい、検知が機能しなくなる。
- `AnalyserNode` で FFT 解析。
  - `fftSize: 4096`（サンプルレート 48kHz で約 11.7Hz 分解能、時間分解能は約 85ms）
  - `smoothingTimeConstant: 0`（平滑化は自前で行うためブラウザ側の平滑化は切る）
- 16,000〜18,200Hz に該当する周波数ビンのパワーを合算。
- 判定：合算値が閾値を下回る状態が保持時間続いたら「停止」。
- 状態が変化したら WebSocket で即座にブロードキャスト。

**画面表示（運営には見せない。自分の確認用）：**

- 現在の帯域エネルギー値（リアルタイム）
- 設定された閾値
- 現在の判定状態（鳴っている / 停止）
- スペクトラム表示（10〜20kHz）— 動作確認用
- キャリブレーションボタン
- 接続中のクライアント数
- 接続用 URL の QR コード

**設定項目（画面上で調整可能に）：**

| 項目 | 初期値 | 備考 |
|---|---|---|
| 監視帯域 下限 | 16000 Hz | |
| 監視帯域 上限 | 18200 Hz | |
| 閾値 | キャリブレーションで自動設定 | 手動でも調整可 |
| 保持時間（停止判定） | 60 ms | 誤検知が出たら伸ばす |
| 保持時間（再開判定） | 30 ms | |

### 4-2. キャリブレーション機能

会場のノイズ環境は事前に分からないため、当日その場で調整できる必要がある。

**手順：**

1. 「環境ノイズ測定」ボタン → 音が鳴っていない状態で 3 秒間測定 → ノイズフロアを記録。
2. 「音源測定」ボタン → 運営に音を鳴らしてもらった状態で 5 秒間測定 → 音楽時のレベル分布を記録。
3. 閾値を自動算出（音楽時の中央値から約 25〜30dB 下、かつノイズフロアより十分上）。
4. 算出結果を画面に表示し、手動調整も可能にする。

測定値は `localStorage` に保存し、次回起動時に復元する。

### 4-3. WebSocket サーバー

技術： Node.js + `ws` パッケージ

- 静的ファイル配信（Mac 側検知ページ、iPhone 側受信ページ）。
- WebSocket で全クライアントへブロードキャスト。
- ポート：8080（任意）。
- 起動時にローカル IP アドレスをコンソール出力。

**メッセージ形式（例）：**

```json
{
  "type": "state",
  "playing": true,
  "level": 42.3,
  "threshold": 15.0,
  "timestamp": 1234567890123
}
```

- 状態変化時に即座に送信。
- 加えて、生存確認のため定期送信（例：500ms ごと）も行う。

### 4-4. iPhone 側：受信ページ

技術： HTML + JavaScript。PWA 化（ホーム画面に追加可能に）

**画面合図（メイン）**

既定の合図方向（`合図:鳴音中`モード）：

- 高周波が鳴っている間： 画面全体を白黒の高速点滅（約 10Hz）＋持続音。
- 高周波が止まった瞬間： 暗転（点滅停止）＋無音。 → この「急にチカチカと音が消える」変化が着席の合図。

`合図:停止時`モードに切り替えると旧方式（鳴っている間は暗転、止まったら点滅＋音）になる。当日どちらが反応しやすいか試して選ぶ。

設計根拠：

- 人間の周辺視野は色の判別が苦手だが、明暗の急変と動きの検出には非常に敏感。
- そのため色替え（緑 → 赤）より白黒のコントラスト、静的変化より点滅が有効。
- スマホを手に持って腕を下ろした状態でも視界の端で気づける。
- 画面いっぱいのベタ塗りにする（アイコンや文字ではなく面積で気づかせる）。

明暗の切替方向は設定で反転できるようにする（当日どちらが見やすいか試して選ぶ）。

**音声合図（サブ）— 採用方式：B（一定音ゲート方式）**

- 合図が出ている間（既定＝高周波が鳴っている間）：持続音（440Hz、小音量）を鳴らし続ける。
- 合図が外れた瞬間（既定＝高周波が止まった瞬間）：持続音を止め、無音にする。 → 音の消失が着席の合図。
- **実装方式：** 検知結果の `playing` 状態で `OscillatorNode` の `GainNode` をゲートするだけ。受信側の WS 状態から鳴らせるため、受信端末にマイク（getUserMedia / HTTPS）は不要。
- 検討したが不採用の方式：A（高周波を低周波にリアルタイム変換してイヤホンに流す＝ヘテロダイン方式）。連続アナログで先読みできる強力な方式だが、AudioWorklet による DSP・ローカルマイク・HTTPS が必要で重い。将来の独立モジュール（有線イヤホン前提の切り札）として保留。

**iOS の制約と対応：**

- **iOS Safari は Vibration API に非対応。** 振動は使用できない。
- iOS はユーザー操作なしの音声再生をブロックするため、開始前に画面を一度タップして音声再生をアンロックする必要がある。開始画面に「タップして開始」を必ず設ける。

**イヤホン使用時の重要な注意：**

- Bluetooth イヤホン（AirPods 等）には **150〜300ms の遅延**がある（Bluetooth 音声の原理的な制約）。
- そのため画面が先に変化し、0.2〜0.3 秒後に音が届く。
- 運用方針：**画面＝本命のトリガー、音＝確認・保険。**
- 音を待ってから動くクセをつけると遅くなる。練習段階から「画面で動く、音は後から来るもの」と体に入れる。
- 有線イヤホンが使えるなら遅延 10ms 程度まで下がるため、そちらが望ましい。

**その他の要件：**

- 画面輝度は最大に固定。
- スリープ無効（Screen Wake Lock API、非対応時はフォールバックとして無音ループ動画等）。
- 画面 / 音 はそれぞれ個別に ON/OFF 切り替え可能。
- 接続状態の表示：WebSocket が切断されたら明確に警告する。
  （無音なのが「音が止まった」のか「単に繋がっていない」のか区別できないと事故になる）
- 現在の帯域レベルの簡易表示（デバッグ用、本番では非表示にできること）。

### 4-5. フォールバック：iPhone 単体検知

PC が使えない / 通信が切れた場合の保険。実装コストはほぼゼロ（Mac 側の検知ロジックと同じコードを iPhone のブラウザで動かすだけ）。

- iPhone 受信ページに「自分のマイクでも検知する」トグルを設ける。
- 判定は **OR 方式**（Mac または iPhone のどちらかが「鳴っている」と言えば鳴っている）。
- iPhone のマイクは 18kHz 付近で感度が落ちるが、15〜16kHz ならかなり拾える。
- → 序盤〜中盤は単体でも戦える。終盤の高い帯域で Mac の精度が効いてくる。
- **注意：** iOS では `getUserMedia` が HTTPS（セキュアコンテキスト）必須。この機能を使う場合は HTTPS 配信が要る。

### 4-6. 練習モード（優先度：低）

余力があれば実装する。

- アプリ自身が音源 mp3 を再生し、反応訓練ができる。
- 特にイヤホンの遅延に体を慣らす目的で有用。
- 反応時間の計測・記録があると理想的。

## 5. ネットワーク構成

会場（体育館）の Wi-Fi 環境が不明なため、外部ネットワークに一切依存しない構成とする。

### 採用案：自分の iPhone のテザリングをホストにする

```
[iPhone A（自分）] ← テザリング親機
        ├── Mac
        └── iPhone B（相方）
```

**設定上の注意：**

- 「互換性を優先」を ON にする（2.4GHz 帯になり、体育館のような広い空間で電波が届きやすい。速度は不要で到達距離を優先）。
- iOS のテザリングは接続機器がないと自動でオフになる。競技開始前に必ず Mac と相方のスマホを繋ぎ、繋ぎっぱなしを維持する。
- データ通信量はほぼゼロ（Mac↔iPhone 間はローカル通信で完結し、モバイル回線を通らない）。
- 自分の iPhone は「親機 兼 受信機」の二役。バッテリー消費が大きいので満充電にしておく。

### 接続手順

1. iPhone A でテザリングをオンにする。
2. Mac をそのテザリングに接続。
3. Mac で Node.js サーバーを起動。
4. Mac 画面に表示された QR コードを両 iPhone でスキャン → ブラウザで受信ページが開く。
5. 受信ページで「タップして開始」→ 音声アンロック。
6. キャリブレーション実行。

### 予備案

- **プラン B：** macOS の Wi-Fi メニューから「ネットワークを作成」（アドホック）。iPhone 側の接続が不安定な場合あり。
- **プラン C：** iPhone 単体検知に切り替え（4-5 参照）。

## 6. 遅延の内訳

| 区間 | 遅延の目安 |
|---|---|
| マイク入力 → FFT 解析 | 10〜30ms |
| 保持時間（デバウンス） | 60ms |
| WebSocket（ローカル） | 10〜50ms |
| 画面描画 | 16〜50ms |
| **画面合図の合計** | **約 100〜150ms** |
| （参考）Bluetooth イヤホン経由の音声 | 上記 + 150〜300ms |

聴こえている人は遅延ゼロで反応できるため、**画面合図を主軸にして遅延を最小化することが競技上きわめて重要。**

## 8. 実装優先順位

1. **Mac 側の検知ロジック（16-18.2kHz 帯域エネルギー判定）** — 最重要。ここが動かなければ何も始まらない。
2. WebSocket サーバーとブロードキャスト。
3. iPhone 側の画面合図（黒 ⇄ 白点滅）。
4. **キャリブレーション機能** — 当日の会場環境に対応するため必須。
5. **接続断の警告表示** — 事故防止のため必須。
6. iPhone 側の音声合図（B：一定音ゲート方式）。
7. iPhone 単体検知のフォールバック。
8. 練習モード（余力があれば）。

## 10. 補足：検知アルゴリズムの疑似コード

```javascript
// 初期化
audioContext = new AudioContext()
stream = getUserMedia({
  audio: {
    echoCancellation: false,   // 必須
    noiseSuppression: false,   // 必須
    autoGainControl: false     // 必須
  }
})
analyser.fftSize = 4096
analyser.smoothingTimeConstant = 0

binWidth = sampleRate / fftSize
lowBin  = floor(16000 / binWidth)
highBin = ceil(18200 / binWidth)

// 毎フレーム
getFloatFrequencyData(buffer)   // dB値の配列
energy = 合算(10^(buffer[lowBin..highBin] / 10))   // dBをリニアに戻して合算
levelDb = 10 * log10(energy)

if (levelDb >= threshold) {
    silenceStartTime = null
    if (state == STOPPED && 継続時間 >= 再開保持時間) {
        state = PLAYING
        broadcast()
    }
} else {
    if (silenceStartTime == null) silenceStartTime = now
    if (state == PLAYING && (now - silenceStartTime) >= 停止保持時間) {
        state = STOPPED
        broadcast()
    }
}
```

**注意点：**

- `getFloatFrequencyData` は dB 値を返すため、合算する前にリニア値に戻すこと。
- ブラウザの `smoothingTimeConstant` による平滑化は応答を鈍らせるため 0 にする。
- 帯域内の全ビンを合算する（ピーク検出ではない点に注意。音楽であって純音ではないため）。
